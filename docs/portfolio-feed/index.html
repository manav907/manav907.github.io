Building a Cyberpunk HDRP Race Track in Tokyo

TOKYO RACETRACK is a Unity HDRP environment project where I built a stylized, neon-lit Tokyo racing scene. I wanted to create a city environment that felt dense and atmospheric, but was also practical to explore, tune, and record for a portfolio.
I brought together Japanese street assets, cyberpunk holograms, skyboxes, city-generation tools, lighting, and reflection probes to shape the scene. The fun part was finding the balance between making it look great and keeping it flexible enough to inspect while moving through it.
To make that easier, I made a small runtime controller attached to the camera. It lets me change reflection quality with the mouse wheel, switch between realtime, time-sliced, on-demand, or disabled reflections, and adjust the camera's render distance with Ctrl + mouse wheel. That meant I could test different visual settings without constantly jumping back into the Unity editor.
I also used occlusion culling, trigger-based lighting groups, and reflection-probe refreshes to keep the scene manageable. Unity Timeline and Recorder were included for capturing the environment once it was ready.
The main goal was to make more than a nice-looking cyberpunk scene: I wanted a space that was easy to tune, inspect, and present. It was a great exercise in combining environment art with the small tools that make a real-time scene easier to work with.

Undead Code and the 20 FPS Curse

At the time, I had only recently joined the company and was still within my first month. I was working on Victorian Murder Mystery as part of the QA team and was still getting familiar with the project, its systems, and the way the team worked.
While testing the game, I started running into some serious performance issues. On my relatively powerful gaming machine, the project was running at around 20 FPS. I asked around to see if anyone else was experiencing the same thing, only to discover that the problem was affecting everyone, and in some cases it was much worse for them, with some team members seeing below 15 FPS and large performance spikes.
It also seemed like the issue had been around for a while and that most people had effectively given up on finding the root cause. Since investigating it wasn't initially part of my responsibilities, I started looking into it informally while continuing with my normal testing.
A lot of testing was being done directly in the Unity Editor, so I began using some temporary settings to make the project more manageable. Eventually, the project manager noticed those settings. Since they were also struggling with the performance, particularly on an older MacBook, they asked me to properly investigate the issue and see if I could find the underlying cause.
That was when the investigation became a more focused debugging task.
Starting With the Obvious
My first step was to investigate whether the problem was primarily coming from the art and asset side of the project.
I had a short video call with the lead 3D artist to go through the performance issues. We identified several areas where the assets and rendering setup could be improved, but it quickly became clear that those changes were not enough to explain the scale of the problem.
There was still a much larger performance cost that we hadn't accounted for.
I moved on to profiling the project in Unity, expecting to find an expensive script or an obvious rendering bottleneck.
Instead, I found very little.
No individual script stood out as the obvious culprit, and nothing on the rendering side immediately explained why performance was dropping so severely.
The more I investigated, the more confusing the problem became.
The Wrong Test
The problem was that I was not reproducing the conditions that were actually causing the performance degradation.
Most of my initial tests were artificial or isolated. They were useful for looking at the project in a controlled environment, but they weren't representative of how the game was actually being tested.
This mattered because Victorian Murder Mystery was a multiplayer project.
I eventually decided to profile the game during an actual multiplayer testing session instead of continuing to test it in isolation.
That was when the first major clue appeared.
When the Players Joined
As players joined the session, performance started to degrade.
At first, I wanted to confirm whether the players themselves were actually responsible for the performance drop. I ran a more controlled test where I focused on adding players and observing the performance impact.
The results seemed to point in that direction, but there was a problem with the test: it was still somewhat artificial. I was isolating the number of players rather than reproducing everything those players were actually doing during a real session.
So while I had confirmed that the issue was related to the multiplayer workflow, I hadn't yet identified the specific action that was triggering it.
Looking more closely at the sequence of events revealed that the performance degradation was particularly noticeable while players were going through the character-selection system.
Then I found an even more specific clue.
Players didn't actually have to select a character. Simply previewing one was enough to cause the problem.
That gave me a concrete interaction to investigate.
I started tracing what happened whenever a player previewed a character.
The Character Preview
The preview system was creating more than just a character model.
Each preview could create a duplicate character model, camera, and lighting setup for displaying the character.
That was already suspicious.
If those objects were being created repeatedly without the previous ones being properly removed, every additional preview could add more work for the game to process.
The next question was why this behavior was happening in the first place.
The answer led to a piece of code that, by all rights, should have been dead.
The Undead Code
The character-selector system had been completely reworked at some point during development.
The old implementation was no longer supposed to be part of the project.
But the old script was still there.
Not only was it still present in the project, it was still attached to objects in the scene and had its related references and objects intact.
The old system had effectively become undead code.
It had been replaced from a feature perspective, but it had never actually been removed from the runtime environment.
As a result, when a player previewed a character, the stale script was still executing its old behavior and creating another preview setup.
The result was a growing collection of unnecessary runtime objects:
Character preview → duplicate model → duplicate camera → duplicate lighting → repeat.
The more players interacted with the system, the more noticeable the performance cost became.
This finally explained why my earlier profiling had failed to reveal the problem. The expensive behavior wasn't simply running continuously. It was being triggered by a specific multiplayer interaction that my artificial tests weren't reproducing.
Tracing the Problem Back Further
Finding the stale script answered what was causing the problem, but I wanted to understand why it had survived the character-selector rework.
That investigation led to a bad merge.
During the rework, the old character-selector system should have been removed along with its associated references and scene objects. Instead, the merge preserved them.
The result was effectively two generations of the system surviving together:
New character-selector system + old character-selector system.
The old implementation was no longer needed, but its script and associated objects remained in the scene and continued to execute.
That made the bad merge the ultimate starting point of the issue.
The chain looked like this:
Bad merge
↓
Old character-selector script survives
↓
Old references and scene objects remain
↓
Player previews a character
↓
Old system creates another model, camera and lighting setup
↓
Repeated previews accumulate unnecessary objects
↓
Multiplayer performance degrades
What initially looked like a broad performance problem was ultimately the consequence of an obsolete system that had survived a merge.
Removing the Curse
Once the root cause was clear, the fix was relatively focused.
The stale character-selector script and its related references and objects were removed so that the old preview behavior could no longer execute.
I then repeated the same multiplayer testing scenario that had exposed the problem and profiled the project again.
The difference was substantial.
Performance on my machine improved from roughly 20 FPS to around 120 FPS.
More importantly, the performance degradation associated with repeatedly previewing characters was no longer occurring.
The temporary settings I had been using to make Editor testing manageable were no longer needed as a workaround for this particular issue.
What Made This Problem Difficult
The most important part of this investigation wasn't the final deletion of the stale script. It was figuring out when and why the performance problem actually appeared.
The initial profiling wasn't useless, but it was being performed against the wrong scenario. There was no obvious script consuming a huge amount of time every frame, and there was no single rendering feature that explained the frame rate.
Even the first multiplayer test needed another layer of investigation. I initially tried to isolate whether the number of players itself was responsible, but that test was still too artificial. It wasn't enough to know who was in the session. I needed to reproduce what they were doing.
The key was reproducing the actual multiplayer workflow.
Once I saw the sequence:
players joining → character preview → performance degradation
the investigation became much more focused.
From there, I could follow the behavior from the preview system to the duplicate objects, from those objects to the stale script, and finally from the stale script back to the bad merge that had allowed it to survive.
The Takeaway
This investigation reinforced a simple principle I try to follow when debugging performance problems:
Before optimizing what is slow, find out what is actually causing the slowdown.
And before assuming that something is expensive because it is poorly optimized, check whether it should exist at all.
The character-selector system had already been replaced. From a feature perspective, the old implementation was dead. But because of a bad merge, the old script and its associated objects were still alive in the scene.
The result was a performance problem that only became obvious when players interacted with the game in the way it was actually intended to be played.
The final path from problem to solution was:
20 FPS → multiplayer profiling → character preview identified as the trigger → duplicate preview objects discovered → stale script found → bad merge traced as the origin → obsolete system removed → roughly 120 FPS.
The code was supposed to be dead.
It just hadn't gotten the memo.

Architecture From Scratch So “One More Mini-Game” Doesn’t Become a Problem

Mini Minds started as a one-week prototype.
The goal was not to build a complete educational gaming platform. It was to answer a simpler question: could we build something like this quickly, and would it actually be valuable?
The prototype answered that question well enough to justify continuing.
But proving that an idea works and building something that can continue evolving are two different engineering problems.
Mini Minds had been built around speed. It was useful for validating the concept, but it wasn't designed for several developers to work on different parts of the product at the same time. As the idea moved beyond the prototype stage, that limitation became more important.
CMAT2 was the successor the game changed a lot under the hood even if it mostly stayed the same overall, a lot more polish was added and 2 new games were added as replacement.
The goal was no longer simply to prove that we could make educational mini-games. We needed a codebase that could support a growing suite of them without turning every new game into another round of duplicated infrastructure.
That changed how I approached the architecture from the beginning.
The Prototype Had Done Its Job
There was nothing inherently wrong with the original Mini Minds structure.
For a one-week prototype, optimizing for speed made sense. The important thing was learning enough about the product to determine whether it was worth pursuing.
The problem was that the assumptions that make a prototype effective are not necessarily the assumptions that make a product codebase scalable.
Mini Minds had demonstrated that the concept could work.
It also gave us a clearer picture of what the eventual product would need.
There would not just be one game.
There would be multiple game modes, levels, progression, player records, results, and eventually synchronization and reporting around those results.
That created a new engineering question:
> If we already know we're going to build more games, what should be designed once rather than rebuilt for every game?
That was the question behind CMAT2.
The First Constraint Was Parallel Development
The first problem wasn't performance.
It wasn't memory usage.
It wasn't even a particular bug.
It was the structure of the codebase itself.
When a prototype grows organically, it is easy for responsibilities to become intertwined. A game controller might know about its gameplay, UI, level setup, completion behavior, and persistence because, at prototype scale, there is little reason to separate them.
That becomes harder when multiple people need to work on the project.
If every game has its own interpretation of how levels start, finish, save, and progress, developers aren't simply working on different games. They are also working on different versions of the same underlying product behavior.
That creates unnecessary coordination.
I wanted CMAT2 to make the common parts explicit.
A developer working on a new game should be able to concentrate on the game's rules without having to reinvent the application's lifecycle.
Looking for What Was Actually Common
The first step was identifying what the games genuinely had in common.
The gameplay itself was not a good candidate.
Match Cards and Number Pop have fundamentally different mechanics. Other modes such as Shape Match, Spot Objects, Spot Differences, Cars Coordination, and Nodulus introduced their own rules and interaction models.
Trying to force those into one generic gameplay system would have created an abstraction that was technically shared but conceptually wrong.
The commonality appeared somewhere else.
Every game needed some version of:
Load → Start → Play → Complete → Record → Progress → Sync
The mechanics changed.
The lifecycle did not.
That became the first architectural boundary.
Building the Common Lifecycle
I introduced BaseGameModeController as the common contract for game modes.
The important decision was not simply using inheritance. It was deciding which responsibilities belonged in the base layer and which remained with each game.
The framework could own the common lifecycle.
The game could own its rules.
Conceptually:
BaseGameModeController
|
+-- Match Cards
+-- Number Pop
+-- Shape Match
+-- Spot Objects
+-- Spot Differences
+-- Cars Coordination
+-- Nodulus
This meant a new game did not need to invent its own interpretation of the application's overall lifecycle.
It needed to implement the parts that were actually unique.
That distinction became important for keeping the architecture reusable without making it overly generic.
Configuration Was a Separate Problem
Once the lifecycle was shared, I needed to solve a different problem: how levels were described.
Different games naturally required different settings.
A Match Cards level needs different configuration from Number Pop. Trying to put every possible property into one universal configuration class would simply move the complexity somewhere else.
Instead, CMAT2 used a shared BaseLevelConfig with game-specific derived configurations.
The campaign could then contain those different configuration types and retrieve the appropriate configuration using a record key.
Campaign
|
+-- BaseLevelConfig
|
+-- Match Cards Config
+-- Number Pop Config
+-- Shape Match Config
+-- Spot Objects Config
+-- ...
This gave the system a useful separation:
The campaign describes what should be played.
The game decides how it is played.
The two could evolve independently.
The Important Discovery Was the Completion Flow
The next architectural boundary became obvious when I followed a level all the way to the end.
A game finishing wasn't the end of the operation.
The game produced a result. That result then had to move through several systems.
The shared flow looked roughly like this:
Level Complete
↓
LevelRecord
↓
Finish UI
↓
Badge Evaluation
↓
Profile Save
↓
Campaign Progress
↓
Server Sync
The LevelRecord became the handoff point.
It captured information such as completion time, errors, interactions, completion timestamp, and synchronization state.
This was useful because the gameplay code didn't need to know how every downstream system worked.
The game produced the evidence of what happened.
The rest of the application could decide what to do with that evidence.
That made the architecture much easier to reason about.
The Record Also Solved a Mobile Problem
Once progress was represented as a local record, server synchronization did not need to be tightly coupled to gameplay.
That mattered because mobile connectivity is not something a game should assume will always be available.
A level could be completed and stored locally even if synchronization wasn't immediately possible.
The record carried its sync state:
Play
↓
Create LevelRecord
↓
Save locally
↓
Unsynced
↓
Batch synchronization
↓
Server confirmation
↓
Synced
The server synchronization layer could also merge remote records into local profile data while avoiding records that already existed locally.
This was another example of keeping responsibilities separate.
Gameplay shouldn't care whether the network is available.
Progress persistence shouldn't require every game to implement its own networking.
And the server shouldn't need to understand the internal mechanics of every mini-game.
The Architecture Was Really About the Next Developer
The prototype had optimized for answering:
> Can we build this?
CMAT2 had to answer a different question:
> Can we keep building this?
That distinction influenced the architecture.
A reusable game lifecycle meant developers didn't need to coordinate around separate implementations of scene loading and completion.
Shared level configuration meant new content could be represented through an established model.
A common LevelRecord meant progress didn't depend on every game inventing its own persistence format.
Shared finish and progression behavior meant the product could remain consistent even as the number of game modes increased.
The framework wasn't intended to make every developer work on the same abstraction.
It was intended to give them stable boundaries so they didn't have to.
Verification: Could a New Game Fit Without Rebuilding the Product?
The practical test was whether the architecture actually reduced the work involved in another game.
The existing modes provided that test.
Match Cards could maintain its own matching mechanics.
Number Pop could maintain its own target, timing, accuracy, and scoring rules.
Other modes could use different configuration types and gameplay logic.
But they could still participate in the same broader flow:
Configure → Load → Play → Complete → Record → Progress → Sync
That was the behavior I wanted to preserve.
The framework had not eliminated game-specific code.
It had eliminated the need for every game to recreate the surrounding product infrastructure.
What I Took Away
The biggest lesson from moving from Mini Minds to CMAT2 was that prototype architecture and product architecture solve different problems.
Mini Minds succeeded because it was fast enough to answer whether the concept was worth pursuing.
CMAT2 had to solve what happened next.
The useful abstraction wasn't "a mini-game."
It was everything that repeatedly happened around a mini-game.
That led to a much more specific rule for deciding what belonged in the framework:
> If every game needs it regardless of its mechanics, it probably belongs in shared infrastructure.
If only one game needs it because of its rules, it should probably stay with that game.
That distinction kept the framework from becoming a giant generic game controller while still giving the project a consistent lifecycle.
And that is what made "one more mini-game" a manageable engineering task instead of another architectural negotiation.

Fixing The root cause of Broken Steam Desktop Icons because everyone else takes the easy way out

After reinstalling Steam, all of my game desktop icons became blank. Creating the shortcuts again through Steam did not fix it either. They were blank as soon as Steam made them.
I knew I could replace every icon manually, one by one, but that sounded painfully tedious. When I looked online, the best alternatives I found mostly automated that same process: they made it quicker to assign replacement icons, but they were still only covering up the problem.
That was not enough for me. As soon as Steam made a new shortcut, I would be back in the same situation. I wanted to know why Steam was creating blank shortcuts in the first place.
Finding the Actual Problem
The games were still there and worked fine. What was missing was the local icon file that each Steam web shortcut points to.
I had kept an external Steam library after reinstalling Steam. Steam could see those existing games, but it did not put their icon files back in its local cache at DefaultSteamInstallDIR\steam\games. That is why clearing Windows' icon cache did not help. Windows cannot show an icon file that is missing.
That was the part that made it click. I did not want a tool that just swapped out icons on my desktop. I wanted to restore the files Steam expected to find, so every shortcut it created would work normally.
Making a Proper Fix
That is why I made FixSteamICON. Instead of changing icons shortcut by shortcut, it puts the missing Steam icon files back where they belong.
It reads Steam's libraryfolders.vdf file to find the games in every library. Then it gets each game's clienticon hash from Steam, downloads the right .ico file from Steam's CDN, and puts it back in DefaultSteamInstallDIR\steam\games.
It does not guess which icon belongs to which game or pull images from some random site. It uses Steam's own data to find the right icon, then restores it locally.
I split it into a small Node.js/Express helper service and a Python script. Node uses steam-user to get Steam product information. Python handles the Windows-side work like picking the Steam folder, reading the library data, downloading icons, and opening the repaired folder. The batch files take care of setup, starting the local service, and refreshing Windows' icon cache afterwards.
It is a fair bit of setup for fixing icons, but it means I do not have to repair dozens of shortcuts by hand and most importantly they fixed the core issue which ment that they are fully compataible with steam's create desktop shortcut feature among other things.
I Was Not the Only One
It is a pretty niche problem. You have to reinstall Steam, keep an old external library instead of downloading everything again, and then create Steam web shortcuts. Still, people kept running into it.
The Reddit post where I shared FixSteamICON kept getting replies from 2024 into early 2026. Some people had reinstalled Windows or Steam and did not want to redownload or revalidate hundreds of gigabytes of games. Others got their Steam web shortcut icons back and called the tool a lifesaver.
The comments also showed me that I had made the tool harder to use than it needed to be. People got stuck on Node, Python, PATH, batch files, ports, and one easy-to-miss detail: the local server window has to stay open while the Python script runs. One person even wrote extra instructions for everyone who came after them. That was helpful, but it also made it clear that my own instructions needed work.
That was a useful reminder that finding the technical fix is only half the job. If the people using it are not developers, setup and documentation are part of the fix too.
What I Learned
FixSteamICON is a small project, but I like what it represents. The easy route was to make the desktop look okay for now. The better route was figuring out why it was broken and fixing that part instead.
It saved me from a tedious cleanup, and the comments showed that other people had hit the same problem. Their games were fine, but Steam had lost the small files that made its shortcuts look normal.
If I came back to it, I would package it as an app or at least make it a one-command install. The repair logic works. The next step would be making it easier for someone else to run.

The Gully Champ Duplicate Dialogue Bug

Context
Gully Champ was a Unity-based visual novel and cricket strategy game that shipped on Steam. It combined card-based cricket gameplay, a calendar-driven story, world navigation, Yarn Spinner dialogue, and scene transitions.
I worked on the application lifecycle layer connecting these systems. I implemented the bulk of it on September 24, and it ran for roughly three weeks without a major issue.
The Problem
On October 15, while we were testing the game, we noticed a duplicate-dialogue issue in one of the story flows.
The affected path was specific: finishing a card gameplay event, moving into a new-day calendar event, and then starting a dialogue event. Instead of the dialogue initializing once, it could initialize twice.
At first, I didn't know where the regression had been introduced.
Rather than immediately changing the dialogue system, I wanted to understand why the lifecycle was reaching the same point more than once.
Initial Investigation
I started by adding targeted logs around the affected transition and checking stack traces. I wanted to see exactly where the duplicate execution was coming from.
The investigation narrowed the problem to the lifecycle transition rather than the dialogue content itself.
I traced the relevant flow and found that the duplicate behavior was happening somewhere between completing gameplay and starting the dialogue.
The first suspects were the dialogue and calendar systems. I checked both, but neither explained why the same lifecycle action could be reached twice.
That shifted my attention toward the transition and loading code.
The Key Clue
I used git log and GitLens to inspect recent changes around the transition code, looking specifically for changes that could affect timing or input availability.
This was where the timeline became important.
The lifecycle system had been implemented on September 24 and had been running without this issue. A large branch had been merged shortly before we discovered the regression.
A teammate had made a relevant change on October 13 involving the loading transition.
The change had disabled the wait that previously kept the transition from progressing until the loading animation had finished.
What made this particularly significant was that the line already had a comment I had added earlier:
//disable locally for fast testing; do not commit; needs to be refactored for robustness.
The warning was explicit. The wait could be disabled locally for faster testing, but the change was not supposed to be committed.
Despite that, the wait had been disabled and the change had been committed.
I then checked the commit boundary.
I checked out the suspect commit and reproduced the duplicate-dialogue bug. I then checked the commit immediately before it and confirmed that the bug did not occur there.
That gave me a strong correlation between the regression and the transition change.
Root Cause
The wait was part of the transition flow that prevented the lifecycle from continuing before the transition had reached the required state.
Once it was disabled, the transition could progress too early and input could become available before the lifecycle had finished its previous step.
The resulting chain was:
Wait disabled
→ transition progresses too early
→ lifecycle action can be triggered more than once
→ dialogue initialization is reached twice
→ duplicate dialogue
The visible symptom was in the dialogue system, but the regression was in the lifecycle transition.
The Fix
The immediate fix was to restore the transition wait and its associated input-blocking behavior.
I also reviewed the surrounding transition logic because the incident showed that lifecycle timing and input availability were closely connected. Some gameplay behavior had been relying on that blocking as an implicit safeguard.
Finally, I added a lightweight regression check using basic regex matching to catch this specific wait being disabled again.
It wasn't intended to replace behavioral testing. It was simply a cheap guard against repeating the same change that had caused the regression.
Verification
I went back to the original reproduction scenario: finish the card gameplay event, advance the calendar, enter the new-day event, and start the dialogue.
The commit comparison gave me the clearest verification:
- Before the suspect change: no duplicate dialogue.
- With the suspect change: duplicate dialogue reproduced.
- After restoring the wait: duplicate dialogue no longer occurred.
I also verified that the regression check caught the specific disabling of the wait.
This gave me much stronger confidence than simply confirming that the dialogue appeared correctly once after the fix.
Lessons Learned
The biggest lesson was that important lifecycle constraints should be protected, not just documented.
In this case, the code already contained an explicit warning:
//disable locally for fast testing; do not commit; needs to be refactored for robustness.
The intent was clear, but the change was still disabled and committed. That showed me that comments can communicate an important constraint, but they cannot enforce one.
Three lessons stood out.
Trace the lifecycle before blaming the visible subsystem.
The bug appeared as duplicate dialogue, but following the execution path led back to the transition system.
Treat synchronization as correctness.
The wait looked like part of a loading transition, but removing it changed when the lifecycle and input were allowed to progress.
Add lightweight protection around known failure modes.
The regression check was intentionally simple. It didn't replace proper testing, but it added an automated guard around a change that had already caused a real regression.
The final fix was small. The investigation was not.
The useful part of the incident wasn't knowing which line to restore. It was following the evidence from symptom → hypothesis → experiment → commit history → root cause → fix.
In a game where multiple systems depend on the same lifecycle, a tiny timing change can become everybody's problem.

Validating Narrative Content in Gully Champ

Gully Champ was a visual novel and cricket strategy game, so it had a lot of moving parts: branching Yarn dialogue, character expressions, background changes, calendar-driven scenes, world navigation, and gameplay data. The challenge was not only building those systems, but making sure new story content could be added without quietly breaking the game.
A major part of that challenge came from how the narrative content was produced. Much of the dialogue was written separately and in parallel, with the Yarn dialogue in particular being worked on by many different people. Each character also required a large number of sprite variations. Some characters had character-specific emotion sets, while others used a shared set of emotions conceptually but still required separate sprite assets for each character.
Because sprite preparation took significant time, the writing and implementation work could not always wait for the final assets to be ready. Duplicate sprite mappings were therefore sometimes used as a temporary solution so that parallel work could continue. This was useful for keeping production moving, but it also introduced another class of content problems that needed to be caught later.
That workflow made small inconsistencies surprisingly difficult to track down. An incorrect character name, incorrectly named sprite, missing sprite reference, or duplicate mapping could cause a scene to behave incorrectly. Some problems were obvious, but others were much more subtle. A sprite might technically exist but be mapped to the wrong character, or a temporary duplicate could remain in place without being immediately noticeable.
Without automated validation, finding these issues often meant manually playing the game and waiting for the problematic scene to appear. Even then, some errors were subtle enough that they would not immediately look like bugs, meaning they might not even be identified as the source of a problem. A mistake several steps earlier in a dialogue sequence could only become apparent once the scene was being presented to the player.
These were the problems the validation tools were primarily designed to solve.
I built Unity Editor validation tools around these failure points. The tools parsed Yarn commands, checked their parameters, validated character and expression names against the project enums, and confirmed that the required sprites actually existed through the dialogue sprite mappings. They also checked calendar entries against valid Yarn nodes and validated presentation rules, such as narration or choices appearing while character sprites were still on screen.
For example, if a writer used an invalid SetCharacterExpression command, the validator could identify the command and report its missing or incorrect arguments before the scene was played. If a sprite was missing or incorrectly referenced, the tool could report the broken mapping directly. Instead of discovering a bad scene during a playthrough and then tracing the problem back through potentially hundreds of lines of dialogue, the issue was surfaced directly in the editor.
The goal was not to produce a report containing every theoretical warning. It was to make the warnings useful enough that the team would actually act on them. After filtering out noisy or low-value results, roughly 700 possible QA issues were reduced to 52 actionable ones. That distinction mattered. A report full of false positives quickly becomes background noise, while a focused report gives writers and developers a concrete list of problems worth investigating.
These checks were part of a broader validation system covering other content and presentation rules as well. However, the cross-references between dialogue, characters, emotions, and sprites were a particularly important problem because they sat directly at the intersection of many people working on the project in parallel.
The rest of Gully Champ had its own complexity: a world map, date-based progression, rewards, and a cricket card system involving timing, bowling variations, targets, and tutorial flow. The narrative validation tools helped make the story side dependable enough to work alongside those systems rather than becoming a fragile handoff between writing and gameplay.
Gully Champ reinforced something I value about production tooling: as content grows, the tools used to validate that content become part of the game development process itself. Turning fragile, designer-authored workflows into reliable automated checks meant that the team could work in parallel, move faster, and catch problems without relying entirely on someone manually playing through the game and hoping to notice them.

Time Travelers from Laos Were Playing Our Game

We were pushing a new ad campaign and comparing the ad monetization data with our Firebase player data to make sure everything lined up.
While digging through the incoming players in Firebase, something caught my attention.
Each document had a perfectly normal Firebase timestamp everything looked fine.
But there was also an old, leftover device timestamp field that we normally don't even look at.
That timestamp said:
2568.
At first, I thought someone had changed their phone clock.
So I filtered the Firebase documents by that year.
And suddenly, there were a lot more records about 30 players with around 130 score submissions.
Different players. Different devices. Different dates.
I chuckled and thought:
“Wait… are we getting players from the future?”
During our lunch break, I mentioned the strange timestamps to our CEO.
I was expecting a funny response.
Instead, he panicked.
He thought it might be some kind of bot attack and that having strange data like this could raise red flags with AdMob.
He was probably worried because I had previously explained to him that bot farms exist and, in theory, can be used to farm ad revenue.
And while AdMob would likely detect that kind of activity pretty quickly, their policies also put some responsibility on us as developers to make sure our apps aren't being exploited by invalid traffic or bot farms even accidentally.
If AdMob decided we were knowingly using bots to generate ad revenue, that could get our account permanently banned.
I wasn't particularly worried about a bot farm, though.
I'd already built some pretty good tooling for detecting suspicious gameplay: an .replay viewer, touch-interaction heatmaps, and frequency analysis.
So I had plenty of ways to investigate whether these were actually bots.
After lunch, I went back to the data and started investigating it manually.
Eventually, I noticed something else.
A lot of these players were from Laos.
That was the clue.
I started looking into how dates and calendars are commonly handled in the region, and that's when the whole thing started making sense.
The Buddhist calendar is widely used and familiar in Laos, alongside the Gregorian calendar. In the Buddhist Era system, the year is 543 years ahead of the Gregorian year.
So:
2568 = 2025.
2569 = 2026.
Suddenly, the mysterious "future" timestamps weren't mysterious anymore.
The devices weren't actually telling us that it was the year 2568 in the Gregorian sense. They were using a calendar system where 2568 is the local Buddhist Era representation of 2025.
And this was exactly the kind of thing that can happen when software crosses cultures and regions. Heck there is a whole calendar app for this country Lao Calendar - ປະຕິທິນລາວ
In this case, it wasn't necessarily that individual users had gone into their settings and manually changed their calendars. The devices themselves can be configured by the OEMs for the conventions commonly used in that region, including the local calendar system.
So from the user's perspective, everything was completely normal.
Their phone was just displaying and providing dates according to the calendar convention configured for that market.
So while we were looking at players coming in through our new ad campaign, we accidentally crossed paths with a completely unrelated piece of localization behavior that had been sitting quietly in our database for a long time.
The funny part is that our Firebase timestamps had been perfectly correct the entire time.
The important timestamps the ones we use for things that actually need to represent real points in time come from internet/server-based time.
The weird device timestamp was only there for some old, lightweight offline features, things like figuring out:
“You last played 2 days ago.”
It was never being used as the source of truth for anything important.
So after understanding what was happening, I didn't actually need to fix anything.
There wasn't a broken Firebase timestamp.
There wasn't a bot farm.
There wasn't an AdMob attack.
And, unfortunately, there weren't any time travelers either.
It was just a device using a different calendar convention.
Our new ad campaign had simply led us down a rabbit hole that ended in internationalization.
**No time machine.
Just internationalization.**

From Jump Game to Mochi the Blob: Taking a Game From Idea to Market

Mochi the Blob was one of the first projects we started at Alpha Code Labs.
Before Mochi, we had been working on a cricket game. We eventually decided to pivot toward making smaller games that we could develop and ship more quickly, with the goal of expanding our portfolio and learning from a wider range of products.
One of the first projects to come out of that shift started with a simple idea inspired by Jump King.
Internally, we called it Jump Game.
The premise was straightforward: a vertical platformer where the player works their way upward through increasingly difficult spaces. But the reason we were interested in Jump King wasn't simply that it was difficult. It was the way it created difficulty.
Traditional platformers such as Super Mario often depend on precise timing and quick reactions. You are moving, jumping, reacting to enemies, and making decisions under constant pressure. That works well with a controller, but we wanted something that could translate cleanly to a mobile screen with a much simpler control scheme.
Jump King offered a different kind of challenge. The jumps could be calm and calculated. There was no constant pressure from a timer. The pressure came from the possibility of making the wrong decision and falling.
That seemed like a good fit for mobile.
Simple controls did not have to mean simple gameplay.
From a Three-Person Prototype to a Product
The project started with three people, and I led the charge.
I was responsible for overall direction, core development, and technical leadership. I also broke the work down into tasks, assigned work to the other team members, reviewed their code, and handled technical issues that crossed team boundaries, including source-control problems in Plastic SCM.
At the beginning, we were primarily trying to answer one question:
Was this core movement actually fun?
The prototype let us focus on that without having to build the entire game around it. We experimented with the jump, movement, camera, and early level layouts until the mechanic started to feel like something we could build a product around.
Once that happened, the problem changed.
We needed to turn a mechanic into a game.
That meant creating levels, progression, scoring, collectables, onboarding, and the systems connecting them. The project gradually grew from a prototype into something that had to make sense as a complete player experience.
I started treating level information as data rather than something that existed only inside individual Unity scenes. LevelDataSO became the model for things such as level references, difficulty, level size, and jump-count grading thresholds.
That allowed other parts of the game to work from the same information. The level-select screen could show the zone, level number, difficulty, and size, while player records could provide best times, jump counts, and collectable progress.
The implementation itself wasn't the interesting part.
The important change was that levels were no longer just content. They had become part of the product's progression model.
Discovering What the Prototype Didn't Tell Us
One assumption that changed was how easy the movement would be for a new player to understand.
We knew how Mochi worked because we had been building and testing it constantly. New players didn't.
The jump arc wasn't always interpreted the way we expected, and that made the first interaction more important than we had initially assumed. If a player misunderstood the movement, they could become frustrated before discovering what made the game enjoyable.
That pushed us toward iterating on onboarding: tutorial timing, first-time guidance, hint direction checks, and hint bubbles.
The lesson was simple but important: a mechanic can be technically correct without being understandable.
Making It Ready for the Real World
As development progressed, the definition of "done" kept expanding.
Having finished levels wasn't enough. We needed progression, player records, daily tasks, leaderboards, backend services, analytics, and monetization.
I worked across those areas as the project moved toward release, including Firebase parameters, leaderboard architecture, and the migration from Firebase Realtime Database to Cloud Firestore.
Monetization was another area where we initially kept our options open. The game supported AdMob, IronSource, and Unity Ads, with the advertising provider separated from the core game logic so we could evaluate different setups without tightly coupling the rest of the game to one provider.
As we moved toward production, we ultimately settled on AdMob as the default advertising provider. The flexibility was useful during development, but shipping required making a concrete production choice.
By this stage, "the game" meant more than the gameplay itself. It included the progression systems, UI, backend, analytics, advertising, platform configuration, and everything required to get the product onto a real device and store.
Publishing Is Its Own Engineering Problem
Getting the game ready for Google Play was not simply a matter of uploading an APK and waiting for it to appear.
Publishing required a different kind of work: completing the required compliance information, preparing store assets, hosting a privacy policy, configuring the store listing, and making sure the product met the requirements necessary to actually be distributed.
There was another complication on our side.
Although the project team for Mochi was small, Alpha Code Labs as a whole had grown to around 13 people, and I was the only person on the team with previous hands-on experience actually publishing games to Google Play.
My first published title had been released in 2018 and was no longer live by the time we were working on Mochi. I had also released another title in 2020, so while I wasn't approaching Google Play publishing for the first time, I was still working with a platform whose requirements and processes had to be handled carefully.
That experience became useful beyond Mochi.
I led the publishing requirements for Mochi and subsequently helped handle the publishing process for more than ten other titles we worked on at Alpha Code Labs.
This was an important shift in my role. I wasn't only responsible for getting the game technically ready. I became one of the people responsible for getting the product through the final gap between "it works on our devices" and "it is actually available to players."
Publishing Changes the Problem
Once Mochi was released on Google Play, the source of our information changed again.
Before release, most of our feedback came from ourselves and the people directly involved in development. After release, actual players became another source of evidence.
Player behavior could challenge assumptions we had made during development. If players struggled with a level, for example, the problem wasn't automatically the level itself. It could have been the onboarding, the way the progression was presented, the hints, or simply the point at which the player encountered the challenge.
That meant post-launch work became a loop:
Observe → understand → change → observe again.
Analytics helped provide quantitative signals, while qualitative observations helped explain what those signals meant. Difficulty, retries, and player confusion were no longer hypothetical concerns. They were things we could observe in the context of a shipped product.
But something else became clear after release:
Development hadn't actually stopped.
Shipping Wasn't the End
Mochi continued to receive development after launch.
We worked on regular updates, new features, DevOps, maintenance, fixes, and the infrastructure required to keep the game running as a live product.
That changed the way I thought about the relationship between development and release.
A traditional development milestone makes it tempting to think in terms of a finish line: build the game, submit the game, get it approved, and move on.
Mochi didn't really work that way.
Once people were playing, the product had to keep changing with them. New features had to fit into the existing game. Updates had to be delivered reliably. Backend systems had to continue functioning. Bugs that never appeared during development could emerge under real-world conditions.
The product was no longer something we were preparing for players.
It was something that existed with players.
Then We Had to Market It
After getting the game into players' hands, another problem became impossible to ignore:
How do you make someone care about the game before they've played it?
A player inside Mochi already has enough context to interact with the game. We can teach the controls, show the jump arc, let them experience the consequences of falling, and gradually introduce the rest of the game.
Someone seeing an advertisement has none of that context.
We approached the problem at several levels.
First, we created a playable ad that took the core interaction and adapted it into an advertising format. We worked with Luna Playworks and its playable-ad tooling to explore how much of Mochi's gameplay could be communicated through direct interaction.
The challenge was to strip the experience down without losing what made it recognizable. The player needed to understand the basic interaction almost immediately, while still getting a sense of the calculated jumping and the consequences of making a bad move.
We also created a video advertisement designed specifically to be engaging rather than simply functioning as a recording of gameplay. Instead of asking someone to interact, the video had to capture attention and communicate the appeal of Mochi quickly.
That distinction mattered.
A gameplay clip shows what the game looks like. An advertisement has to communicate why someone should care.
We then distributed advertising across multiple platforms, including Instagram, Facebook, YouTube, and the Google Play ecosystem, using the Meta and Google advertising platforms.
Alongside paid advertising, we also produced organic social-media content for Instagram, YouTube, and Facebook.
The organic posts did not generate the level of traffic that some of the team expected. That outcome was broadly in line with what I expected going in. Creating content and having an audience that reliably converts that content into game traffic are two different problems.
For me, the useful takeaway was that distribution has to be evaluated separately from content production. A post can be well made without necessarily generating significant traffic, and visibility does not automatically translate into installs.
Working across the playable ad, video advertising, paid acquisition, and organic social content made the relationship between game development and marketing much clearer.
The audience had simply changed.
During development, we were asking whether we could make the mechanic work.
During onboarding, we were asking whether a new player could understand it.
During marketing, we were asking whether someone who had never seen the game could understand enough to want to try it.
When the Leaderboard Became People
One of the more rewarding parts of continuing to operate Mochi was watching the leaderboard become more than a feature we had implemented.
People were actually competing on it.
We celebrated players who reached the top of the leaderboards, and those players came from countries including Peru, the Philippines, Bangladesh, India, Malaysia, Brazil, Honduras, Jamaica, Pakistan, Egypt, Argentina, Mongolia, and Iraq.
Seeing those names and countries appear in the game changed the scale of what we had built.
The project had started with three people experimenting with a movement mechanic.
Now someone halfway around the world could open the game, play the levels we had built, compete for a position on a leaderboard, and become part of the product's ongoing story.
Real players also produced some surprisingly strange technical stories. One of them became an article of its own: "Time Travelers from Laos Were Playing Our Game".
That incident was a good example of the kinds of problems that only appear once software is operating in the real world. The full investigation is better covered separately, but it became one of the more memorable reminders that shipping a game means dealing with data, infrastructure, and player behavior you could never completely anticipate during development.
Looking Back at the Journey
Mochi started because we wanted to make smaller games.
The original idea was deliberately constrained: take the calculated jumping of Jump King, simplify the controls, and see whether that kind of challenge could work on mobile.
From there, the project expanded into a complete product: levels, progression, scoring, collectables, onboarding, backend systems, analytics, monetization, publishing, player feedback, marketing, live updates, and DevOps.
What changed wasn't just the amount of work involved. The problem itself kept changing.
At first, we were solving a game-design question.
Then we were solving a production question.
Then a publishing question.
Then a player-understanding question.
Then a communication and acquisition question.
And after all of that, we were solving the much less glamorous but very real problem of keeping the product alive.
The most useful thing I took from the project was how connected those stages really are. The same core mechanic had to survive every transition: it had to be fun, understandable, shippable, observable, marketable, and maintainable.
Mochi started as three people experimenting with a prototype called Jump Game. It became a shipped mobile product, and then something more interesting: a product with real players, ongoing updates, competition, operational requirements, and an audience spread across the world.
The biggest change wasn't when we published it.
It was when the game stopped being something we were building for ourselves and became something other people were actually building experiences around.
That's when the product really started.

Building a 27KB Taskbar Overlay

I use Win + 1, Win + 2, and the rest of the numbered taskbar shortcuts all the time. They are wonderfully fast until I have enough windows open that I cannot remember what Windows considers the first, second, or seventh button.
So I made NumberedTaskbar: a tiny Windows utility that shows the shortcut number over each taskbar button while the Windows key is held down. Press Win, glance at the taskbar, and the mapping is right there. Let go and it disappears.
The whole native executable came out to about 27KB. That is not a goal in itself, but it captures the spirit of the project: do one small thing, stay out of the way, and make a repeated bit of friction disappear.
The tiny annoyance
The taskbar already has the shortcut system. The missing piece is visibility.
When I am moving quickly, I do not want to pause and count icons or hover over them. I want the same immediate feedback that a keyboard-driven workflow normally gives me. A number overlay turns the shortcut from something I vaguely remember into something I can use without thinking.
That is the kind of problem I enjoy building utilities for. A tiny improvement used dozens of times a day is often more valuable than a big feature that looks impressive but rarely gets opened.
Making it feel like part of Windows
The visible feature is simple. The implementation is less so.
The app watches for the left or right Windows key with a low-level keyboard hook. While either key is down, it puts a transparent, click-through, always-on-top window over the virtual desktop. That window does not steal focus or block clicks; it only draws the labels.
To figure out where to draw them, the utility looks at the taskbar through Microsoft UI Automation. It finds the visible taskbar buttons, removes duplicates, keeps the useful first row and first ten entries, then uses their bounds as the positions for the overlays.
The rendering side is old-school Windows in a satisfying way: Win32 for the window and message loop, Direct2D for the little label backgrounds, and DirectWrite for the numbers. DWM and shell notifications help it stay in sync with the desktop, while display-change messages make sure the overlay still fits if monitors are rearranged.
None of that is especially flashy. It is mostly a collection of rules for being a polite desktop utility: appear quickly, draw cleanly, do not intercept input, survive taskbar changes, and clean up after yourself.
Prototype first, then go native
I also made an earlier C# Windows Forms prototype. It was useful for quickly answering the awkward questions: can I enumerate taskbar items this way, can I reliably notice the Windows key, and what does the Windows 11/XAML taskbar expose through UI Automation?
Once those answers were clear, the C++ version made more sense. It was a better fit for a small native process and gave me direct control over the overlay, rendering, COM lifetime, hooks, tray icon, and shutdown path.
The prototype was not wasted work. It was the fast way to reduce uncertainty before committing to the lower-level version.
The lesson from a 27KB app
Small utilities are a great excuse to learn the parts of an operating system that larger apps often hide behind frameworks. This one touched keyboard hooks, window z-order, transparent layered windows, UI Automation, graphics resources, and multi-monitor layout all to show a few numbers.
That sounds slightly ridiculous, and it is. But the result fits neatly into my everyday workflow, which is the point. The best personal tools do not demand attention. They quietly remove one tiny reason to slow down.

Cutting RAM Use in Half by Doubling the Build Size

Context
Around my second month at Idea Usher, I was given a fairly straightforward-sounding task on the VeeLive Metaverse Project: make the Unity WebGL application work reliably on mobile browsers.
VeeLive is a multiplayer metaverse built with Unity and C#, targeting both desktop and mobile WebGL. It includes multiplayer presence, proximity-based voice through Photon Voice, in-game screen sharing through WebRTC, multiple environments, and a CI/CD pipeline that deploys WebGL builds to AWS.
The mobile controls were not the difficult part.
The difficult part was getting the application to survive on mobile devices.
The Problem: The App Would Simply Die
On most Android phones I tested, the behavior was inconsistent but understandable. The build would usually load, but when I tried loading a particularly large environment such as the Shopping Mall, Chrome would sometimes crash with an “Aw, Snap!” page indicating that the tab had run out of memory.
iPhones were stranger.
Instead of showing an obvious out-of-memory error, the page would silently reload at roughly the same point during loading. After a couple of attempts, Safari would eventually show a generic “Can’t Open the Page” message.
There was no useful crash message telling me what had actually failed.
That gave me several possible explanations. The build was large, WebGL was running inside a browser, and the failure happened while loading large environments. My first suspicion was therefore that the build itself was simply too large for mobile.
That turned out to be only part of the story.
Investigation: Separating the Failure Modes
The initial WebGL build was around 480 MB, so investigating the build size was a reasonable place to start.
The build size was also more relevant to runtime memory than simply treating it as a downloadable file. A Unity WebGL application does not run like a native executable. It runs inside a browser environment, where the JavaScript engine, WebAssembly, loaded build data, and browser/runtime overhead all contribute to the page's memory footprint.
That meant the 480 MB build was already contributing to the application's baseline memory usage before the runtime assets for a large environment were loaded. Scenes, textures, meshes, materials, and other runtime allocations then added memory on top of that.
So the initial suspicion that the build was too large was reasonable. I just did not yet know how much of the problem came from the build itself and how much came from what the application loaded on top of it.
On iPhones, the behavior was different enough that I had to treat iOS as a separate part of the investigation.
In this environment, I found that iOS imposed hard resource restrictions on web applications that were not obvious from the browser's failure behavior. Safari's theoretical storage quota also could not be treated as guaranteed capacity. A device might theoretically support a much larger quota, but that did not mean the application could safely assume that amount of storage would be available in practice. As available storage became more constrained, eviction and write failures became increasingly relevant.
This mattered because the original WebGL build was around 480 MB. When Data Caching was enabled, builds around the 500 MB range could trigger storage-related failures on some iPhones. In those cases, the page could be forcibly terminated without leaving useful application logs behind.
That explained part of the behavior I was seeing, but it still did not explain why the application could crash after the caching issue was removed.
I disabled Data Caching and retested.
The caching-related failure disappeared, but the application could still crash when loading large environments.
That was an important turning point. I had removed one possible cause and the underlying problem was still there.
The investigation shifted from:
“Is the build too large to cache?”
to:
“How much memory does the WebGL application actually consume while running?”
Getting Evidence From the Devices
I already understood that the RAM advertised for a device was not equivalent to the amount available to a browser application. An 8 GB phone does not give a WebGL page an 8 GB memory budget.
What I needed to establish was how that limitation behaved on the actual devices we were targeting.
Debugging the iPhone failures was particularly difficult because I did not have direct Safari developer-tool access to the devices available for testing.
With the final logs often disappearing when the page reloaded, I could not rely on a clean crash report to tell me what had happened.
I therefore approached the problem through multiple pieces of evidence: memory snapshots, available logs, repeated reproduction tests, and observations across different devices and browsers.
The behavior was not identical everywhere. Some devices crashed, some managed to load further, and different browsers behaved differently.
Across the devices where I could reproduce the issue, however, a pattern emerged.
Going beyond roughly 1,350 MB of runtime memory caused crashes on many of the target devices.
I would not treat 1,350 MB as a universal WebGL, iOS, or Android limit. It was an observed practical boundary in our testing environment. But it gave me something much more useful than the device's advertised RAM: a measurable target for the application.
At that point, the problem was no longer simply “mobile browsers don't like the build.”
I had evidence that the application was exceeding the practical memory budget available to it.
The next question was the important one:
What was consuming all that memory?
Discovery #1: Too Much Content Was Being Loaded
The first major discovery was in the way the project handled its assets.
The original VeeLive build was not using Unity Addressables. The project had been optimized mainly around having fewer files and smaller file sizes, which helped keep the overall build compact.
That approach had an unfortunate consequence for a memory-constrained WebGL application.
Too much content could remain available in memory even when it was not relevant to the environment the user was currently viewing.
The Shopping Mall made the problem particularly obvious.
It was a large environment containing a significant amount of geometry, textures, materials, and other assets. Those assets could contribute to memory usage even when the user was actually inside a much smaller environment such as a small office.
The application was effectively carrying around content that the user did not currently need.
I introduced Unity Addressables and restructured the project so that each environment could be packaged as its own independently loadable file.
Instead of treating the project as one large collection of content, scenes could be loaded dynamically when required.
The goal was straightforward:
Load the content needed for the current environment, rather than keeping unnecessary environments resident in memory.
There was an interesting trade-off. Splitting the project into independently loadable Addressable files dramatically increased the overall build size.
For this project, that was worth it.
I was deliberately trading build size for lower peak runtime memory usage. The application was failing because of memory pressure, so a larger collection of downloadable files was preferable to a smaller build that consumed too much RAM once running.
Addressables solved the first major memory problem: asset residency.
But it exposed another question.
Even after reducing how much content was loaded, how expensive was the content that remained?
Discovery #2: Texture Memory Was a Separate Problem
The second discovery was that some individual assets were consuming far more GPU memory than their compressed versions needed.
Texture format made a substantial difference.
Resolution | RGB32 | Compressed (4 bpp) | Memory Saved | % Saved
--- | --: | --: | --: | --:
512 × 512 | 1 MB | 0.125 MB | 0.875 MB | 87.5%
1024 × 1024 | 4 MB | 0.5 MB | 3.5 MB | 87.5%
2048 × 2048 | 16 MB | 2 MB | 14 MB | 87.5%
4096 × 4096 | 64 MB | 8 MB | 56 MB | 87.5%
A single 4096 × 4096 texture could therefore represent a difference of roughly 56 MB of memory compared with RGB32.
Across a large environment containing many textures, those differences added up quickly.
The project also had to support different desktop and mobile texture capabilities. Instead of manually overriding texture formats in individual .meta files, I changed the loading approach so the application could select an appropriate compressed format based on the device's supported texture formats.
Where supported, formats such as ASTC could significantly reduce the memory cost of loaded textures.
This was separate from the Addressables problem.
Addressables controlled how much content was resident.
Texture optimization controlled how expensive that resident content was.
I also removed or optimized unnecessary materials, sprites, meshes, placeholder assets, and other large environment resources that were contributing to the footprint.
Root Cause
By this point, the failure was much clearer.
It was not caused by one oversized scene or one browser limitation.
The practical root cause was excessive peak memory usage in a browser environment with a much smaller usable memory budget than the device's advertised RAM suggested.
Several factors compounded the problem:
- The WebGL application had a substantial baseline memory footprint.
- The original loading strategy kept more project content resident than was necessary.
- Large and inefficiently formatted textures increased the cost of the content that remained loaded.
The iOS caching issue was real, but it was a separate failure mode, rather than the complete explanation for the runtime crashes.
Fix and Verification
The fixes followed the problems uncovered during the investigation.
I first disabled Data Caching to remove the separate iOS storage-related failure.
I then introduced Addressables and split the environments into independently loadable scene files, reducing unnecessary runtime asset residency.
Next, I optimized the assets themselves, including device-aware compressed texture loading and cleanup of unnecessary materials, sprites, meshes, textures, placeholders, and large environment assets.
Finally, I reduced the baseline WebGL build footprint so that less memory was consumed before the heavier runtime content was loaded.
The overall measured runtime memory footprint dropped from approximately 2.1 GB to 1.02 GB.
The important part was not just the number.
I retested the same large environments that had previously caused mobile browsers to crash. The problematic environments could now load within a much more manageable memory range on the target devices.
The result came from several independent changes rather than one magic optimization: removing the caching failure mode, controlling asset residency, reducing the cost of loaded assets, and lowering the baseline WebGL footprint.
Interestingly, the final build was larger than the original in terms of downloadable files, largely because of the way the project had been split with Addressables.
That was acceptable.
The goal was never to produce the smallest possible build. It was to produce a build that could actually run reliably within the memory constraints of the devices we were targeting.
Lessons
1. Device RAM is not the browser application's memory budget
I already understood this principle before the investigation, so it was not itself a discovery.
What I had to establish was how that constraint behaved on our actual devices. The roughly 1,350 MB practical boundary came from testing, not from treating a device specification as an application memory limit.
I also had to explain this distinction to others on the project. Seeing a device with 4 GB or 8 GB of RAM can make it tempting to assume that the WebGL application has access to something close to that amount. In reality, the available memory depends on the operating system, browser, device, and other processes competing for memory.
2. WebGL memory problems have multiple layers
The build footprint and runtime asset usage are different contributors, but they ultimately compete within the same constrained browser environment.
Reducing only one of them was not enough.
The investigation worked because I stopped treating “memory usage” as a single number and looked at where that memory was coming from.
3. When the platform hides the failure, change the conditions
The iPhone crashes initially gave me almost no useful information.
Disabling caching did not solve the entire problem, but it removed one failure mode and exposed another that could be measured.
That turned an apparently silent browser failure into an investigation with a reproducible memory boundary, concrete evidence, and a measurable target for optimization.
The final result was a useful reminder that in WebGL, making the build larger can sometimes be the right trade-off if it means making the running application smaller.
